# IBEIS Code Smells & Windows-Packaging Triage

Compiled 2026-07-16 while diagnosing the Windows installer crash in the Advanced ID
interface (`OSError: could not get source code` from `utool.util_inspect.get_func_sourcecode`
under PyInstaller). Findings were gathered by a full-repo sweep and the load-bearing
claims were spot-verified by hand. File references are to the `add_submodules` branch.

Priority key:

- **P0** — blocks the packaged Windows app from working
- **P1** — real bug / will bite users or developers
- **P2** — hygiene, debt, or papercut

Items marked ✅ were fixed during the 2026-07-16 session (details inline; the changes
live in `dev/_installers/ibeis_pyi_helper.py`, `ibeis_app_entry.py`, and
`build_installer.ps1`). Fix verified on Linux: a frozen build passes
`IBEIS_FROZEN_SELFTEST=1`, and hiding the bundled `ibsfuncs.py` reproduces Nate's exact
`OSError` — confirming both the diagnosis and the fix.

## 1. Frozen-app (PyInstaller) hazards

### 1.1 ✅ P0 — Runtime source introspection vs. bytecode-only bundle (the Nate crash)

IBEIS/utool parse *function source code at runtime* (`ut.get_func_sourcecode`,
`ut.parse_func_kwarg_keys`, `ut.recursive_parse_kwargs`, `ut.exec_funckw`, doctest
harvesting, ...). PyInstaller ships only bytecode inside the PYZ archive, so
`inspect.getsource` raises `OSError: could not get source code` — exactly the crash in
Nate's log (`guiback.py:180` → `ibsfuncs.parse_annot_config_stats_filter_kws` →
`ut.parse_func_kwarg_keys`).

Two layers of fix:

- Commit `c57c40d39` already replaced the two specific call sites with a static
  autogenerated schema (`ibeis/other/_autogen_stats_schema.py`). Nate's traceback line
  numbers (4575/4926) match the *pre-fix* code — **his installer was built before that
  commit landed**, so a stale build is part of the story.
- The systemic fix (this session): bundle the `.py` sources of the whole ecosystem
  (`ibeis`, `utool`, `vtool_ibeis`, `dtool_ibeis`, `plottool_ibeis`, `guitool_ibeis`,
  `futures_actors`, `pyhesaff`, `pyflann_ibeis`, `vtool_ibeis_ext`, `ubelt`) as
  PyInstaller datas so `inspect.getsource` works everywhere
  (`dev/_installers/ibeis_pyi_helper.py::SOURCE_INTROSPECTED_PKGS`). A frozen self-test
  (`IBEIS_FROZEN_SELFTEST=1 IBEIS-console.exe`) now exercises this path in
  `build_installer.ps1 -Checks`.

Residual inventory of introspection call sites in `ibeis/` (for eventual removal —
shipping sources is a workaround, not a cure):

- Runtime-reachable but **argspec-safe** (no source read): `algo/hots/chip_match.py:1451,2611`
  (`ut.get_kwargs(ChipMatch.initialize)`), `algo/verif/clf_helpers.py:296`.
- Dev/CLI-only source readers: `_ibeis_object.py:223` (behind `--autogen-core`, and uses
  Py2-only `func.func_code` — dead on Py3, see 3.6), `algo/graph/refresh.py:223`,
  `control/controller_inject.py:987`.
- ~30 doctest-only sites (`ut.exec_funckw` etc. in `gui/guiback.py`, `annotmatch_funcs.py`,
  `control/manual_*_funcs.py`, `web/routes.py:3118`, ...). Doctests double as the test
  suite, so these keep the source-bundling requirement alive even for CI-built exes.

### 1.2 P1 — Unconditional module reload in the annotation editor

`ibeis/viz/interact/interact_annotations2.py:64,144` call `interact_annotations.rrr()`
(an `importlib.reload`) inside `if True:` **every time the image annotation editor
opens**. Reload of a frozen module is loader-dependent and can raise; it is also
gratuitous in production. Delete the `rrr()` calls (they are dev hot-reload scaffolding).
Related dev-only reload hooks: `gui/guiback.py:2935`, `viz/viz_graph.py:639`,
`viz/interact/interact_matches.py:262`, `algo/detect/fasterrcnn.py:35`.

### 1.3 P1 — `__file__`-relative web assets without a `_MEIPASS` guard

`ibeis/web/apis_detect.py:222`, `ibeis/web/apis_query.py:455,1074` build static CSS/JS
paths from `dirname(abspath(__file__))` with no frozen-app guard, unlike
`controller_inject.py:112-118` which does it right. Currently rescued by the spec's
`collect_data_files("ibeis", includes=["web/*", "web/**/*"])` placing files at the same
relative paths — verify the web UI in a frozen build before calling this fixed, and
prefer the `controller_inject` pattern everywhere.

### 1.4 P1 — Torch-importing modules are force-hidden-imported but torch is excluded

`ibeis_pyi_helper.py` adds **every** `ibeis` module as a hiddenimport, including
`ibeis/algo/verif/torch/*` (top-level `import torch`), while the spec `excludes=["torch"]`.
Those modules are present-but-broken in the exe; any code path that imports them crashes.
Either exclude `ibeis.algo.verif.torch*` from hiddenimports or make the imports lazy.
There is no coherent "torch is optional" story: `conda_requires.py` lists torch, pip
requirements never do (see 5.3).

### 1.5 P2 — `exec`/`eval` scaffolding in the production entry path

`ibeis/__main__.py:125-138` (`run_ibeis`) ends in a `<DEBUG CODE>` block: it always does
`ibs = main_locals['ibs']` (KeyError if no db is opened) and, under `--cmd`,
`exec(execstr)` on a utool-generated code string. `ibeis/dev.py` has ~6 more
`eval`/`exec` sites. Dev conveniences living in the shipped entry point.

## 2. Windows-specific runtime hazards

### 2.1 P0 — Default workdir is a *relative* path → resolves into `C:\Program Files\IBEIS`

`ibeis/init/sysres.py:83-93`: `get_workdir()` reads the cached workdir with
`default='.'`, and when unset returns the bare relative string
`'ibeis_default_workdir'`. For an installed app launched from its install dir, every
default DB/cache path lands under `C:\Program Files\IBEIS\...` → `PermissionError` for
non-elevated users (or worse, silently works when elevated and hides user data in
Program Files). The stray `ibeis_default_workdir/` directory at this repo's root is this
exact bug firing on Linux. Fix: default to a per-user location, e.g.
`ub.Path.appdir('ibeis', type='data') / 'workdir'` or `~/Documents/IBEIS`.
Everything in `IBEISControl._init_dirs` / `sysres.db_to_dbdir` inherits this.

### 2.2 P1 — Text I/O without `encoding=` (locale is cp1252 on Windows)

No production `open()` call in the package passes `encoding=`. Worst case:
`ibeis/control/manual_name_funcs.py:1191,1194,1212` — the name-change JSON audit log.
Renaming an animal to any non-cp1252 string via the GUI raises `UnicodeEncodeError`
inside the rename flow. Also `manual_imageset_funcs.py:1412` (smart XML read). Systemic
audit needed; start with control/gui/dbio.

### 2.3 P1 — `open('/dev/null', 'w')`

`ibeis/algo/detect/selectivesearch.py:138`, `ibeis/algo/detect/darknet.py:212` — use
`os.devnull` (on Windows this creates a literal file or errors).

### 2.4 P1 — Path splitting on literal `'/'`

`ibeis/other/detectcore.py:146` (`image_path.split('/')` → wrong filenames in export on
Windows), `ibeis/dbio/ingest_ggr.py` (9 sites). Plus 28 uses of `ut.unixjoin` on
GUI/control paths (`IBEISControl.py:980,1016`, `gui/guiback.py:372,515,1636`, ...) —
usually tolerated by Windows but defeats path comparisons.

### 2.5 P1 — Writes into the installed package directory

`ibeis/_ibeis_object.py:265` and `ibeis/control/controller_inject.py:987-988` write
autogenerated `.py` files into the package dir (read-only under Program Files). Dev
codegen paths, but they hard-fail if triggered from an installed app.
Also `ibeis/viz/viz_graph.py:808-809` (`open('fig.html', 'w')`) and
`ibeis/algo/verif/deploy.py:147` write to CWD.

### 2.6 P1 — GUI menu action respawns the frozen exe

`ibeis/gui/guiback.py:3786-3790` `update_source_install()` runs
`ut.python_executable() + ' super_setup.py pull'`. In a frozen app `sys.executable` is
the GUI exe and `super_setup.py` is not shipped — the menu item relaunches the app or
no-ops. Hide/remove it in frozen builds (`getattr(sys, 'frozen', False)`).

### 2.7 P2 — Wildbook integration is Unix-only

`ibeis/control/wildbook_manager.py:607` (`os.system` with `sudo sh -c`), `:636,672,695`
(hardcoded Tomcat `startup.sh`/`shutdown.sh`). If the Wildbook menu items are exposed on
Windows they will fail; gate them by platform.

### 2.8 P2 — Misc

- `os.umask(0o000)` in `main_module.py:206` runs on every `main()`; its doctest also
  drops `tempfile1.txt`/`tempfile2.txt` into CWD (the junk at repo root). World-writable
  umask is a questionable default even on Linux.
- Deep cache trees (`<workdir>/<db>/_ibsdb/_ibeis_cache/...`) + long db names can reach
  MAX_PATH; `chip_match.py:27` already caps filename length (80 on win32) but directory
  depth is unbounded. Consider enabling long-path awareness in the installer
  (manifest/registry) or keeping cache roots short.
- `ut.symlink` in `scripts/thesis.py`, `scripts/_thesis_helpers.py`,
  `scripts/classify_shark.py` — needs admin/dev-mode on Windows; scripts-only.
- Detection backends `darknet/ssd/fasterrcnn/selectivesearch` hardcode
  `~/code/<repo>` checkouts and Unix binaries (`./darknet`, `matlab`); confirm the
  packaged default detector never routes there.
- `graph_server.py:95` treats WIN32 like Linux for `ProcessActor` — verify it works
  under the `spawn` start method.

## 3. Startup / import-time smells

### 3.1 P0 — `argparse` runs at *import* time

`ibeis/params.py:167-171`: importing `ibeis` (transitively `ibeis.params`) parses
`sys.argv` through a large argparse tree. In a frozen GUI exe argv is whatever Windows
passes (file associations, shell handlers, PyInstaller argv emulation on macOS), and
import-time parsing makes `import ibeis` behavior depend on the host process's command
line (breaks embedding, pytest, Sphinx — which is why the env-var escape hatch below
exists).

### 3.2 P1 — The escape hatch env var is typo'd

Same block keys off `os.environ.get('IBIES_PARSE_ARGS', 'ON')` — **IBIES**, not IBEIS.
Anyone "fixing" the spelling silently re-enables import-time parsing; anyone setting the
correctly-spelled var gets no effect.

### 3.3 P1 — ~53 module-level argv reads across the package

`X = ut.get_argflag(...)` / `ub.argflag(...)` at module top level (e.g.
`constants.py:310-339`, `main_module.py:11-13` `QUIET`/`USE_GUI`, `core_annots.py:1497`,
throughout `algo/hots/*`). Behavior is decided by argv *at first import* — wrong for a
GUI app, wrong for spawned multiprocessing children (they re-import with the parent's
argv), and untestable. Long-term: funnel through an explicit config object.

### 3.4 P2 — utool coupling

703 distinct `ut.*` symbols, 8060 call sites; utool is pinned `>=2.2.0` on PyPI while
the `tpl/utool` submodule sits at `v2.1.6-68-g...`. utool's global argv parsing is on
the critical import path (see 3.1/3.3).

### 3.5 P2 — `dependencies_for_myprogram()` hack

`ibeis/__main__.py:15` exists only to help PyInstaller discover imports; the spec's
hiddenimports sweep now does this properly. Remove once the installer story settles.

### 3.6 P2 — Py2 remnants

158 files with `from __future__`, 88 importing `six` (59 `six.moves`, 26
`add_metaclass`, 29 direct `.iteritems()`-style calls), 45 old-style `super(X, self)`,
1 `unicode(`. `_ibeis_object.py:223` still touches `func.func_code` (Py2-only attr).
Mechanical `pyupgrade`/`sixer` sweep would clear most of it; `six` is also dead weight
in the frozen bundle.

## 5. Dependency smells

1. **P1 — Two sources of truth for the ecosystem deps.** `requirements/runtime.txt`
   pins `utool>=2.2.0` etc. from PyPI while `tpl/` submodules pin specific mid-stream
   commits (`utool v2.1.6-68`, `plottool_ibeis premerge-master-jan-26-625`). The CI
   installer job checks out submodules recursively but then installs `.[headless]` —
   i.e. **from PyPI, the submodules are ignored**. Decide: either the installer builds
   from submodule sources (`uv pip install -e tpl/utool ...`) or the submodules are
   documentation. Until then "works on my machine" and CI builds can differ.
2. **P1 — `boto` (Python-2-era, v2) is a runtime dep but never imported** (only
   mentioned in docstrings). Pure bloat in every install and the frozen exe.
3. **P1 — Imported but missing from requirements:** `torch`/`torchvision`
   (`algo/verif/torch/*`, `algo/detect/lightnet.py`), `tqdm` (`lightnet.py:9`),
   `theano` (`web/apis_query.py:575` — abandoned upstream).
4. **P2 —** `six`, `lockfile` (its own comment says "deprecate in favor of fasteners"),
   `setuptools>=34.1.0` as a runtime dep, `cachetools` never imported directly.
5. **P2 —** `conda_requires.py` (5 packages incl. torch) disagrees with pip
   requirements entirely.
6. **P2 —** pin style is inconsistent; `pyzmq` has two overlapping `<3.13` markers;
   a `networkx` comment says "Python 3.12" on the `>=3.13` line.
7. **P2 —** `pip install ibeis` (runtime only) ≠ `pip install -r requirements.txt`
   (runtime+tests+optional).

## 6. Installer / CI smells

1. ✅ **P0 — `Ensure-InnoSetup` only looked in `%LOCALAPPDATA%\Programs`**
   (`build_installer.ps1`). GitHub runners have ISCC preinstalled in
   `C:\Program Files (x86)\Inno Setup 6`, and winget machine-scope installs land there
   too — the Inno step threw even with ISCC present. Likely why the Windows installer
   job died on CI. Now searches Program Files (x86)/Program Files/LOCALAPPDATA/PATH.
2. ✅ **P1 — `_collect_dir_as_binaries` only collected `.dll`/`.pyd`** — Linux/macOS
   builds silently dropped `.so`/`.dylib` (e.g. `pyflann_ibeis/lib/libflann.so`), so any
   non-Windows PyInstaller build was broken out of the gate. Now collects all shared-lib
   suffixes, including versioned sonames.
3. **P1 — No macOS installer CI job.** Only `dev/_installers/mac_dmg_builder.sh` (old,
   references HotSpotter-era layout) and `Info.plist` exist. If a macOS build matters, a
   `build_macos_installer` job mirroring the Windows one (PyInstaller `.app` + DMG) is
   the path; the helper is now cross-platform enough to try.
4. **P1 — `release.yml` never builds/attaches the installer** — installer artifacts only
   exist as per-run CI artifacts (30-day expiry), never on releases.
5. **P2 — Version duplication:** `win_installer_script.iss:4` hardcodes
   `AppVersion "2.4.1"`, duplicating `ibeis/__init__.py::__version__`. Pass
   `/DAppVersion=$(python -c ...)` from `build_installer.ps1` instead.
6. **P2 — Smoke test is weak:** launches the GUI exe for 20 s and only warns on
   failure. The new `IBEIS_FROZEN_SELFTEST` check is a real gate; extend it over time
   (import sweep, opendb on a temp dir, query on testdb1).
7. **P2 — `.travis.yml` (11 KB) is dead** alongside GitHub Actions.
8. **P2 —** `excludes=["torch", "tensorflow"]` in the spec vs. hiddenimports pulling
   torch-importing modules (see 1.4).

## Suggested triage order

1. **Rebuild + reship the Windows installer** from this branch (Nate's build predates
   `c57c40d39` *and* the source-bundling fix). Verify with
   `IBEIS_FROZEN_SELFTEST=1` and the Advanced ID dialog. (§1.1, §6.1)
2. **Workdir default** (§2.1) — the next crash Nate will hit after the introspection
   one, since any "new database" flow writes into Program Files.
3. **CI**: confirm the Windows installer job goes green with the ISCC fix; add the
   selftest as a hard gate; then decide the PyPI-vs-submodule install story (§5.1)
   so CI builds match local ones.
4. `encoding='utf-8'` audit (§2.2), `/dev/null` + `split('/')` fixes (§2.3, §2.4) —
   small, mechanical, high user impact.
5. Remove `rrr()` reloads + `update_source_install` menu item from frozen builds
   (§1.2, §2.6).
6. Import-time argv parsing (§3.1-3.3) — biggest structural fix; unblocks embedding
   and makes multiprocessing-spawn behavior deterministic.
7. Dependency cleanup (§5) and Py2 sweep (§3.6) — mechanical, large diff, do after the
   above so review noise doesn't bury real fixes.
8. Hygiene (§7) whenever convenient.
